# 状态卡「在等你」的三种来源：审批事件 + 未返回的人工闸门工具

状态卡只有三个状态：`running`（进行中）/ `done`（已完成）/ `waiting`（在等你）。
`waiting` 的 chip 文案按原因分三种：**等你审批 / 等你回答 / 计划待审**。
本文写清每种是怎么从会话日志里认出来的，以及为什么**只认 `approval/asked` 是不够的**（0.3.0 的实际 bug）。

## 症状（0.3.0 用户反馈）

「等你审批状态好像没用，一直都是进行中的。」

## 根因：waiting 只挂在审批事件上，而审批事件在你机器上基本不出现

0.3.0 的 `NoticeTracker` 只有这一条进入 waiting 的路径：

```js
if (type === 'approval/asked') return this.#setPhase(state, 'waiting')
```

`approval/asked` 只在**真的弹出工具审批**时才写（`@deepseek-ai/dsh-user-approval` 的
`approval.request()` 成对写 asked/decided）。而实测本机所有 v4 会话日志：

| 会话 | `approval/policy` | `approval/asked` |
|---|---|---|
| 今天的会话（含 `write:15` `pwsh:17`） | `never` 或 `ask` | **0** |
| 2026-09-23 那批 v3 老日志（当时是真弹审批） | — | 9 |

也就是说：`danger-full-access`（never）当然不弹；`workspace-write` + `ask` 时，
工作区内的写文件/命令**本来就不需要越权**，也不弹。结果是 waiting 永远进不去。

而 DSH 官方客户端认定的「这个人卡住了」其实有三种（`pendingInteraction.kind`）：

| 官方 kind | 官方 chip | 会话日志里有痕迹吗 |
|---|---|---|
| `approval` | 等待审批 | ✅ `approval/asked`（未配 `decided`） |
| `question` | 等待回答 | ❌ 没有专用事件；但有 **`tool/call ask_user_question` 未配 `tool/result`** |
| `plan-review` | 计划待审 | ❌ 同上，工具是 **`exit_plan_mode`** |

后两种是**瞬态交互**（走客户端 Remote Event，`dsh-user-questions` 根本不 append 会话事件），
所以 sidecar 只能靠「工具调用还没返回」这一点来认。

## 修法：把「有 call 没 result」当闸门，但只认 allowlist

`runtime/lib/inspector.mjs`：

```js
const HUMAN_GATE_TOOLS = new Map([
  ['ask_user_question', { kind: 'question', label: '等你回答' }],
  ['exit_plan_mode',    { kind: 'plan',     label: '计划待审' }],
])
```

- `tool/call` 命中 allowlist → 记 `pendingGates.set(callId, gate)` + phase 转 `waiting`；
- `tool/result` 带着同一个 callId 回来 → 删登记；还有人等就继续 waiting，
  否则回合还在跑回 `running`，回合已结束收 `done`。

**必须用 allowlist**：普通工具（`pwsh`、长跑任务）同样是「有 call 没 result」，
那是在干活不是等人。把它当 waiting，卡片会在任何长命令期间误报「在等你」。

配套的三处细节（都有回归）：

1. **拿不到 callId 就不登记**（`callIdOf()` 返回空串即放弃）。登记一个配不上对的 callId
   等于把卡片钉死在 waiting，比误判成 running 更糟。
2. **新回合清空 `pendingGates` / `pendingAsks`**。DSH 的审批对与工具调用都 turn-enclosed，
   新回合开始时不可能还开着；崩溃尾部留下的孤儿登记必须作废。
3. **等的理由变了要重发**（`state.lastWaitKind`）。审批答完但提问还开着时 phase 没变，
   但 chip 要从「等你审批」换成「等你回答」——`#settleWaiting()` 因此在 kind 变化时也返回 true。

## 字段路径（实测，别猜）

`tool/call`：

```json
{ "type": "tool/call", "data": { "turn": 1, "step": 67, "callId": "call_00_gcTX…", "name": "ask_user_question", "arguments": "{\"questions\":[…]}" } }
```

`tool/result`（callId 藏在 message 里，`data.callId` 不存在）：

```json
{ "type": "tool/result", "data": { "turn": 1, "step": 67, "message": { "role": "tool", "source": { "kind": "tool", "callId": "call_00_gcTX…" }, "toolCallId": "call_00_gcTX…" } } }
```

## 证据（2026-10-08 真机日志回放）

把本机 `~/.dsh/sessions/**/session.v4.jsonl.zstd` 全量逐事件喂给 tracker：

- 补丁前：`等你…` 状态 **0 次**（所有会话全程 running/done）。
- 补丁后：**3 次** —— 本次对话 `等你回答@seq506`；crazy_label 会话 `等你回答@seq461`、`@seq662`。
  这三处都是真实的 `ask_user_question` 等待窗口（例：02:31:09 落 `tool/call`，02:31:37 才落 `tool/result`，
  28 秒里用户正在答题，而卡片此前一直显示「进行中」）。

第 1 条是**用户自己正在看的那轮对话**，可当验收用例：DSH 弹问题 → 状态卡立刻变「等你回答」并自动展开；
答完 → 回到「进行中」。

## 以后 DSH 加人工闸门怎么办

allowlist 是**可能过时**的清单：DSH 换工具名（或新增阻塞型工具）时要补。
判断标准是「这个工具的 `execute` 会不会 await 用户」——`dsh-plan-mode` 的
`exit_plan_mode` 与 `dsh-tool-ask-user` 的 `ask_user_question` 是当前仅有的两个。
